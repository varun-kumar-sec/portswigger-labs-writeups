# SSRF with Blacklist-Based Input Filter

## 📌 Lab Overview

This lab demonstrates a **Server-Side Request Forgery (SSRF)** vulnerability where the application attempted to prevent access to internal resources using a **blacklist-based filter**.

The application allowed users to specify a URL that the backend server would request. To defend against SSRF attacks, the developers tried to block dangerous keywords such as:

```text
localhost
127.0.0.1
admin
```

However, the blacklist implementation was flawed and could be bypassed using:

- alternative localhost representations
- URL encoding tricks
- double URL encoding
- filter evasion techniques

This lab focused on:

- SSRF exploitation
- blacklist bypasses
- URL encoding
- double URL encoding
- internal resource access

---

# 🔍 What is SSRF?

**Server-Side Request Forgery (SSRF)** occurs when an application fetches a user-supplied URL without properly validating it.

Instead of making requests to external websites, an attacker can force the server to make requests to:

```text
localhost
internal services
admin panels
cloud metadata endpoints
backend APIs
```

Example:

```text
User Input
↓
http://localhost/admin
↓
Server Requests Internal Resource
```

The attacker cannot access internal systems directly, but the server can.

---

# 🔍 What is a Blacklist Filter?

A blacklist filter blocks specific values considered dangerous.

Example:

```text
Blocked:
localhost
admin
127.0.0.1
```

If the request contains one of these strings, the application rejects it.

---

## ⚠ Why Are Blacklists Weak?

Blacklists only block values developers know about.

Attackers can often bypass them using:

```text
Alternative IP formats
Encoding tricks
Different URL notations
Case variations
```

For example:

```text
localhost
```

can also be written as:

```text
127.1
2130706433
```

which still resolve to the same destination.

# 🔍 Understanding Why Single Encoding Failed

The application likely performed:

```text
URL Decode
↓
Blacklist Check
↓
Forward Request
```

When the server decoded:

```text
%61
```

it immediately became:

```text
a
```

Therefore:

```text
%61dmin
```

became:

```text
admin
```

before reaching the blacklist filter.

As a result, the filter successfully blocked it.

![Screenshot 10](screenshot-ssrf-blacklist10.png)


---

# 🔍 Why Did Double Encoding Work?

Let's break it down.

### First Encoding

```text
a
↓
%61
```

### Second Encoding

The percent sign itself is encoded:

```text
%61
↓
%25%36%31
```

Final value:

```text
%25%36%31dmin
```

---

### Server Processing

First decode:

```text
%25%36%31dmin
↓
%61dmin
```

Blacklist check sees:

```text
%61dmin
```

which does not match:

```text
admin
```

so the request passes validation.

Later, another decoding step occurs:

```text
%61dmin
↓
admin
```

Result:

```text
/admin
```

The backend successfully reaches the internal endpoint.

This is a classic **double URL encoding bypass**.

# ⚠ Why This Vulnerability Exists

The vulnerability existed because the application relied on:

```text
Blacklist Filtering
```

instead of proper validation.

The filter attempted to block dangerous strings such as:

```text
localhost
admin
```

but failed to account for:

```text
127.1
2130706433
Double URL Encoding
Alternative URL Formats
```

As a result, internal resources remained accessible.

# 💥 Impact

An attacker could potentially:

- access internal applications
- reach administrative panels
- bypass network segmentation
- interact with backend services
- delete user accounts
- perform internal reconnaissance
- access sensitive internal functionality

---

# 🛡 Mitigation

To prevent this issue:

- use allowlists instead of blacklists
- validate URLs after full normalization
- block requests to internal IP ranges
- block localhost access
- decode URLs before validation
- prevent multiple decoding stages
- isolate backend services from user-controlled requests
- implement network-level SSRF protections
